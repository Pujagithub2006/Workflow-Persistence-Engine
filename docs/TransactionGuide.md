# Transactions & Concurrency

## Transaction Boundaries

Every write operation happens inside a transaction.

### Manual Transaction Management

```java
EntityManager em = JpaUtil.getEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    // Perform write operations

    tx.commit();   // Changes become permanent
} catch (Exception e) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw e;
} finally {
    em.close();
}
```

### Using `TransactionManager`

```java
TransactionManager.inTransaction(em -> {
    // Perform write operations
});
```

This helper automatically:

- Opens an `EntityManager`
- Begins the transaction
- Commits on success
- Rolls back on failure
- Closes the `EntityManager`

---

# Flush vs Commit

| Action | Description |
|---------|-------------|
| `em.persist(entity)` | Registers the entity in the persistence context. SQL may not be executed immediately. |
| `em.flush()` | Sends pending SQL statements to the database, but the transaction remains open. |
| `tx.commit()` | Commits the transaction, making all changes permanent and visible to other transactions. |
| `tx.rollback()` | Discards every change made since `begin()`. |

> `flush()` only synchronizes the persistence context with the database. It **does not commit** the transaction.

# Optimistic Locking

Entities that contain a `@Version` field automatically participate in optimistic locking.

A typical update generated by JPA looks like:

```sql
UPDATE users
SET display_name = ?, version = version + 1
WHERE id = ?
  AND version = ?;
```

If another transaction has already updated the row, the version no longer matches.

As a result:

- No rows are updated.
- JPA throws an `OptimisticLockException`.

### When to Use

Optimistic locking is the default choice for most applications because it:

- Does not block readers or writers.
- Has very low overhead.
- Works well when conflicts are infrequent.
- Can be handled using retries.

### Typical Retry Pattern

```java
int attempts = 0;

while (attempts < 3) {
    try {
        TransactionManager.inTransaction(em -> {
            User user = em.find(User.class, id);
            user.setDisplayName(newName);
        });

        break;
    } catch (OptimisticLockException e) {
        attempts++;
    }
}
```

# Pessimistic Locking

Use pessimistic locking when a transaction must prevent other transactions from modifying the same row until it completes.

```java
TransactionManager.inTransaction(em -> {
    User user = em.find(
        User.class,
        id,
        LockModeType.PESSIMISTIC_WRITE
    );

    user.setBalance(user.getBalance() - 100);
});
```

This issues a database-level lock (typically `SELECT ... FOR UPDATE`).

While the transaction is active:

- Other transactions attempting to acquire a write lock on the same row must wait.
- Updates are serialized.

### When to Use

Use pessimistic locking only for:

- High-contention records
- Long-running critical updates
- Financial or inventory operations requiring strict consistency

For typical CRUD operations, optimistic locking is preferred.

---

# Choosing the Right Locking Strategy

| Scenario | Recommended Strategy |
|----------|----------------------|
| Typical CRUD operations | Optimistic locking |
| Read-heavy applications | Optimistic locking |
| Occasional concurrent updates | Optimistic locking with retry |
| High-contention counters (e.g., inventory, likes) | Pessimistic locking or atomic SQL updates |
| Long-running business operation on a single record | Pessimistic locking |

---

# Anti-Patterns

Avoid the following:

- Using `PESSIMISTIC_WRITE` for every read operation.
- Retrying optimistic lock failures without any delay or backoff.
- Keeping transactions open while performing external API calls or other slow operations.
- Ignoring `OptimisticLockException`, which can silently overwrite another user's changes.
- Assuming `flush()` permanently saves data. Only `commit()` makes changes durable.

---

# Key Takeaways

1. Every database write should occur inside a transaction.
2. `flush()` sends SQL to the database but does **not** commit the transaction.
3. `commit()` makes changes permanent and visible to other transactions.
4. `rollback()` undoes every change made during the current transaction.
5. `@Version` enables optimistic locking automatically.
6. Optimistic locking detects conflicting updates without blocking transactions.
7. Pessimistic locking prevents concurrent writers by acquiring a database lock.
8. Prefer optimistic locking unless strict row-level locking is required.
